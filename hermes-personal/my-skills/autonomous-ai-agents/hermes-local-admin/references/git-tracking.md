# Git-tracking ~/.hermes

Purpose (Sergio): the private repo is a BACKUP of config, skills we created/customized, local plugins and scripts. Track those generously; leave out sessions, DBs, logs, caches, deps, and reinstallable upstream content ("noise"). Don't argue safety for a private repo or push encryption/key-rotation advice — he accepts credential-storage risk. Keep this policy aligned with the hermes-work repo.

## Setup / first commit
1. Move inline secrets out of config.yaml first. `hermes config get <key>` MASKS secrets (prints `***`), so never pipe it into .env. Read the real value from the YAML in a script that prints nothing, write `NAME=value` to .env, then `hermes config set <key> '${NAME}'`.
2. `git init -b main`, allowlist .gitignore: `/*` then re-include .gitignore, .env.example, README.md, config.yaml, SOUL.md, honcho.json, hindsight/config.json, memories/{MEMORY,USER}.md, hooks/, skins/, scripts/, manifests/, local plugins (parent re-include, `/plugins/*`, then leaf), and `!/my-skills/`.
3. Secrets (no git filter, no .gitattributes): config.yaml holds only `${VAR}` refs; values live in untracked .env. `.env.example` (tracked) = .env with values stripped, regenerated by `python3 scripts/sync-env-example.py` whenever .env keys change. Pre-commit check: `grep -nE '(token|key|secret|password|hash):\s*[^$ '"'"'"]' config.yaml` must print nothing secret. Restore = clone, `cp .env.example .env`, fill values, `hermes auth`.
4. Noise/secrets rules that apply even inside re-included dirs: node_modules/, .venv/, venv/, __pycache__/, *.pyc, *.lock, .cache, my-skills/**/data/, .sync_manifest.json, scripts/*.state.json, *.db*, *.sqlite*, .env*, *.pem, *.key, auth.json, *token*.json, *credentials*.json, *creds*, *-session.json, .*session*.json, *password*.txt. Some skills keep OAuth caches/creds/.env next to SKILL.md.

## Skills layout: my-skills/ vs skills/ (shared with hermes-work)
- `skills.create_dir: my-skills` (`hermes config set skills.create_dir my-skills`): every skill we author or customize lives in ~/.hermes/my-skills/ and is tracked whole; new skills land there automatically — no .gitignore edits, no generator script.
- `skills/` holds only bundled + hub installs, kept pristine and fully ignored. Bundled refresh via `hermes update`; hub ones restore from manifests/skills-snapshot.json.
- Never edit a bundled/hub skill in place. Put local fixes/extra references in a companion skill in my-skills/ (e.g. `hermes-agent-local` for `hermes-agent`).
- Drift check: `hermes skills list-modified` must be empty. If not: `hermes skills diff <name>`, MOVE the delta into the companion, then `hermes skills reset <name>` (re-baseline) or `--restore` (stock).
- Name clash precedence is `skills/` over create_dir, so MOVE (never copy) skills into my-skills/.
- Migrating: tar a backup of skills/ (exclude .venv/node_modules) first; move owned dirs with shutil.move preserving category paths; then grep my-skills for hardcoded `~/.hermes/skills/` paths and fix them (skill .venvs from uv don't embed their path). Verify `hermes skills list` totals are unchanged and moved ones show source `create_dir`. Running gateway/dashboard/webui need a restart to see the new dir.
- Classifying owned vs bundled: `skills/.bundled_manifest` names + `hermes skills list-modified` are authoritative; diffing against hermes-agent/skills by `name:` flags 1-file update leftovers as edits.
- A skill absent from both the manifest and current hermes-agent source is NOT necessarily ours: Hermes leaves retired/renamed bundled skills on disk. Check history before calling it owned: `git -C hermes-agent log --format='%h %s' -1 -- skills/<cat>/<name>/SKILL.md`, and compare content to past versions. Retired ones go to archive/, not my-skills/ (they shadow their replacements, e.g. old github-* vs `github`).
- `skills/<x>` may be a symlink (e.g. to ~/.agents/skills/); git stores the link, not the content — tell the user it isn't backed up.
- Untrack with `git rm -r -q --cached skills && git add -A` (disk untouched).

## Plugins and manifests
- Track local plugins (no upstream git remote of their own; note `git -C plugins/x remote get-url origin` falls through to the parent repo when the plugin isn't its own checkout). Plugins that are their own git checkouts go in the manifest only.
- `hermes plugins pack export > manifests/hermes-pack.yaml` (warns for local-only plugins — those must be tracked) and `hermes skills snapshot export manifests/skills-snapshot.json` (re-run after hub installs).
- Copy hand-written systemd units (~/.config/systemd/user/hermes-*.service) to scripts/systemd/ and ~/.local/bin scripts to scripts/bin/. They're copies — re-copy after editing the live ones.

## Before every commit / push
1. `git status --short` FIRST, before staging. Any modified path you didn't touch in this task (often skill notes edited by another session) stays out: stage your own paths explicitly (`git add <paths>`), not `git add -A`, and name the leftovers to Sergio. `git add -A` silently sweeps other sessions' pending edits into your commit.
2. Review `git diff --cached --stat` and the added paths.
3. Grep the staged diff for token shapes (sk-, ghp_, AKIA, bot tokens, `api_key: <value>`); ignore code/doc mentions. `git ls-files | grep -iE 'cred|session|token|\.env|password'` should list only scripts/docs.
4. Show config.yaml diff highlights (plugins enabled/removed settings, telemetry) to the user.
5. Push only to a PRIVATE remote the user named; verify with `git ls-remote origin main` and `gh repo view <repo> --json visibility`.
- When a flow changes (e.g. secret handling), grep README.md and this skill for the old mechanism and rewrite those docs in the same commit — stale docs describing a removed filter/script mislead the next restore. Keep doc rewrites within what was asked; mention unrequested README/skill edits instead of bundling them.

## Consolidating another Hermes repo (e.g. work profile)
`git fetch` and `git pull --ff-only` first — the user often references changes only on the remote, and policies there evolve fast (re-check before re-porting). Diff its .gitignore, my-skills, scripts and SOUL.md against ours. Bring generic skills/scripts/references (`cp -n` so ours win on shared files); leave employer-specific skills, MCP servers, watchers and persona/SOUL behind; merge overlapping skills instead of keeping both. Before copying a work config pattern, verify the env-var/config names against installed source (e.g. grep the provider for `KEY_ENV`) — skills and .env can use a different name than the native provider reads. Port fixes found here back by telling the user.
