# Validate built-in memory end to end

Use a layered check; configuration, persistence, prompt injection and model recall are separate claims. Load the current memory docs and inspect installed APIs before running helpers.

1. Run `hermes memory status` through `terminal` and inspect only non-secret memory/background-review config. Confirm both stores and the memory tool are enabled as intended; distinguish built-in storage from external providers.
2. Inspect MEMORY.md / USER.md using `read_file` when the user authorizes memory validation. Check actual saved entries, limits and scope, not just file existence. An absent MEMORY.md is normal when no general-memory entry has been saved. Do not import another agent's memories or write junk diagnostic facts into durable memory.
3. Correlate bounded background-review log records with actual persisted state. A `result=memory` log is evidence of a reported review write, not by itself a guarantee of good content or a particular changed entry. Separate semantic duplication/inaccurate preferences from storage failures.
4. Exercise the installed MemoryStore's disk loader and format_for_system_prompt in a short read-only process. Use the active profile's real settings, verify each allowed saved entry reaches the fresh rendered memory block, inspect threat-scan exclusions, and confirm source files did not change. This tests memory loading/rendering, not an entire new model conversation. Avoid launching a second automatic-writing agent against the same profile.
5. Test `session_search` separately with a known prior conversation. If a phrase from the current long-running session returns no matches, browse allowed prior sessions and search a known phrase from one; current-session/lineage exclusions and visibility filters are not proof of a broken FTS index. Do not reindex or mutate SQLite merely because a query is empty.
6. Finish with a truly fresh conversation, not a resumed one. Ask which preferences were loaded from persistent user memory, without file reads/session search. The old transcript would otherwise confound the test. Preferences duplicated in SOUL or skills also confound behavioral recall; distinguish the reported source block and, for a strict test, use an explicitly authorized new fact that exists only in memory.
7. Report each layer as passed, failed or not exercised. A store-to-prompt test is not full fresh-session model recall; a successful USER write is not a separately tested MEMORY write. Respect frozen prompt snapshots: memory saved mid-session appears in a subsequent session snapshot, not by mutating the current system prompt.

For mutation/overflow/batch regression tests, use the canonical isolated test runner or an explicitly temporary memory home, never the user's live memories. Remove temporary fixtures afterwards. Do not disable approval gates or add a canary to real memory just to make a test pass. Known duplicate-call/transport defects are independent and can still affect agent-driven memory operations even when the storage layer passes.
